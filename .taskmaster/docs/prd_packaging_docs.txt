# Packaging and Documentation PRD

<overview>
## Problem Statement
The aggregator needs professional packaging for PyPI distribution, comprehensive documentation for users, and automated release management. Without proper packaging, users can't install via pip. Without docs, adoption is limited. Without CI/CD, releases are manual and error-prone.

## Target Users
- PyPI users wanting `pip install drupal-weekly`
- New users needing setup guides
- Developers contributing to the project
- Release managers publishing new versions
- GitHub users tracking release history

## Success Metrics
- PyPI package installable via pip
- Documentation covers 100% of features
- GitHub Actions automatically publish on git tag
- RELEASES.md auto-generated on every tag
- All commands documented with examples
</overview>

## Capability Tree

### Capability: Documentation Generation
Create comprehensive user and developer docs

- **Description**: Create main README.md with overview

- **Outputs**: README.md
- **Behavior**: Overview, quick start, features, installation, links

#### Feature: Usage Guide
- **Description**: Create USAGE.md with detailed examples
- **Inputs**: CLI interface, examples
- **Outputs**: docs/USAGE.md
- **Behavior**: Command syntax, flags, examples, workflows

#### Feature: Provider Guide
- **Description**: Create PROVIDERS.md with AI setup
- **Inputs**: Provider configs, API key sources
- **Outputs**: docs/PROVIDERS.md
- **Behavior**: Setup steps per provider, pricing, model selection

#### Feature: Configuration Guide
- **Description**: Create CONFIGURATION.md
- **Inputs**: Config schemas
- **Outputs**: docs/CONFIGURATION.md
- **Behavior**: Document config.json, providers.yaml, .env

#### Feature: Development Guide
- **Description**: Create CONTRIBUTING.md
- **Inputs**: Project conventions
- **Outputs**: docs/CONTRIBUTING.md
- **Behavior**: Setup, testing, PR guidelines, code style

### Capability: PyPI Packaging
Prepare project for pip installation

#### Feature: Setup Configuration
- **Description**: Create setup.py or pyproject.toml
- **Inputs**: Project metadata, dependencies
- **Outputs**: pyproject.toml
- **Behavior**: Define package metadata, dependencies, entry points

#### Feature: Manifest Definition
- **Description**: Define files to include in package
- **Inputs**: Project structure
- **Outputs**: MANIFEST.in
- **Behavior**: Include docs, configs, exclude tests

#### Feature: Version Management
- **Description**: Single source of truth for version
- **Inputs**: Git tags, version file
- **Outputs**: __version__ variable
- **Behavior**: Read from VERSION file or git tag

#### Feature: Entry Points
- **Description**: Define command-line scripts
- **Inputs**: Main modules
- **Outputs**: Console script entry points
- **Behavior**: Map `drupal-weekly` command to index.py main()

#### Feature: Package Build
- **Description**: Build distribution packages
- **Inputs**: Source code, setup config
- **Outputs**: .tar.gz and .whl files
- **Behavior**: Run `python -m build`, generate dist/

### Capability: GitHub CI/CD
Automated testing and publishing

#### Feature: CI Workflow
- **Description**: Run tests on push/PR
- **Inputs**: GitHub Actions config
- **Outputs**: .github/workflows/ci.yml

#### Feature: Release Workflow
- **Description**: Publish to PyPI on git tag
- **Inputs**: Git tag event
- **Outputs**: .github/workflows/release.yml
- **Behavior**: Build package, publish to PyPI, create GitHub release

#### Feature: Version Detection
- **Description**: Extract version from git tag
- **Inputs**: Git tag (v1.2.3)
- **Outputs**: Version string (1.2.3)

#### Feature: Test Matrix
- **Description**: Test on multiple Python versions
- **Inputs**: Python versions list
- **Outputs**: Matrix test results
- **Behavior**: Test on 3.10, 3.11, 3.12

#### Feature: PyPI Publishing
- **Description**: Upload package to PyPI
- **Inputs**: Built packages, PyPI token
- **Outputs**: Published package
- **Behavior**: Use twine or official PyPI action

### Capability: Release Management
Automated release notes and versioning

#### Feature: RELEASES.md Generation
- **Description**: Auto-generate release notes
- **Inputs**: Git commits since last tag
- **Outputs**: Updated RELEASES.md
- **Behavior**: Parse commits, categorize, format as Markdown

#### Feature: Git Hook Integration
- **Description**: Pre-commit hook to update RELEASES.md
- **Inputs**: New git tag
- **Outputs**: Updated RELEASES.md, committed
- **Behavior**: Detect tag, generate notes, amend commit

#### Feature: Changelog Formatting
- **Description**: Format commit history as changelog
- **Inputs**: Git log
- **Outputs**: Markdown changelog section
- **Behavior**: Group by type (feat, fix, docs), format with links

#### Feature: Version Bumping
- **Description**: Script to bump version
- **Inputs**: Bump type (major, minor, patch)
- **Outputs**: New version number
- **Behavior**: Update VERSION file, create git tag

- **Inputs**: License text from choosealicense.com
- **Outputs**: LICENSE file

#### Feature: License Headers

- **Inputs**: Source files

<test-strategy>
## Test Pyramid

```
        /\
       /E2E\       ← 10% (Full install from PyPI, test commands)
      /------\
     /Integration\ ← 20% (Package build, CI workflows)
    /------------\
   /  Unit Tests  \ ← 70% (Release notes generation, version parsing)
  /----------------\
```

## Coverage Requirements
- Line coverage: 80% minimum (higher for code, lower for docs)
- Documentation coverage: 100% of features
- CI workflow: Test all supported Python versions

## Critical Test Scenarios

### PyPI Package
**Happy path**:
- `pip install drupal-weekly`, run command
- Expected: Install succeeds, command available

**Edge cases**:
- Install from source, editable install
- Expected: Both work correctly

**Error cases**:
- Missing dependencies, wrong Python version
- Expected: Clear error messages

### GitHub Actions
**Happy path**:
- Push to main, CI runs tests
- Expected: Tests pass, coverage report

**Release path**:
- Create git tag, release workflow triggers
- Expected: Package built, published to PyPI, GitHub release created

**Error cases**:
- Test failures, PyPI upload failure
- Expected: Workflow fails, clear error logs

### Release Notes
**Happy path**:
- Generate notes from git log
- Expected: Formatted Markdown with commits grouped

**Edge cases**:
- No commits since last tag, first release
- Expected: Handle gracefully, appropriate messages

## Test Generation Guidelines
- Test package build on all supported Python versions
- Verify documentation examples actually work
- Test release workflow on TestPyPI first
- Use mock git repos for release script tests

</test-strategy>

<architecture>
## System Components
- **build**: Python build tool (PEP 517)
- **twine**: PyPI package upload
- **GitHub Actions**: CI/CD automation
- **git**: Version control and tagging

## Data Models

```python
PackageMetadata = {
    "name": "drupal-weekly",
    "version": str,          # From VERSION file or git tag
    "description": str,
    "author": str,
    "license": "GPL-2.0",
    "python_requires": ">=3.10",
    "dependencies": list[str],
    "entry_points": {
        "console_scripts": [
            "drupal-weekly=index:main"
        ]
    }
}

ReleaseNote = {
    "version": str,          # e.g., "1.2.3"
    "date": str,             # YYYY-MM-DD
    "changes": {
        "features": list[str],
        "fixes": list[str],
        "docs": list[str],
        "breaking": list[str]
    }
}

CIWorkflow = {
    "name": str,
    "on": list[str],         # push, pull_request, etc.
    "jobs": dict             # test, lint, coverage
}
```

## Technology Stack
- **pyproject.toml**: Modern packaging (PEP 621)
- **build**: Package builder
- **twine**: PyPI uploader
- **GitHub Actions**: CI/CD
- **git**: VCS

**Decision: pyproject.toml vs setup.py**
- **Rationale**: Modern standard, cleaner, PEP 621 compliant
- **Trade-offs**: Requires pip 21.3+
- **Alternatives considered**: setup.py (legacy)

**Decision: GitHub Actions vs other CI**
- **Rationale**: Free for open source, integrated with GitHub
- **Trade-offs**: Vendor lock-in (acceptable)
- **Alternatives considered**: CircleCI, Travis (more complex)

**Decision: Auto-generate vs manual RELEASES.md**
- **Rationale**: Consistency, no manual errors, always up-to-date
- **Trade-offs**: Less human polish (acceptable)
- **Alternatives considered**: Manual (error-prone)

</architecture>

<risks>
## Technical Risks
**Risk**: PyPI publish failures
- **Impact**: High - new version not available
- **Likelihood**: Low
- **Mitigation**: Test with TestPyPI, validate package first
- **Fallback**: Manual upload with twine

**Risk**: GitHub Actions quota limits
- **Impact**: Medium - CI stops running
- **Likelihood**: Low
- **Mitigation**: Optimize workflows, use caching
- **Fallback**: Local testing, manual release

**Risk**: Documentation drift
- **Impact**: Medium - docs out of sync with code
- **Likelihood**: Medium
- **Mitigation**: CI checks for doc updates, review process
- **Fallback**: Manual doc audits

## Dependency Risks
**Risk**: build/twine API changes
- **Impact**: Medium - publish process breaks
- **Likelihood**: Low
- **Mitigation**: Pin versions, monitor deprecations
- **Fallback**: Manual package building

## Scope Risks
**Risk**: Over-complex release process
- **Impact**: Medium - hard to maintain
- **Likelihood**: Low
- **Mitigation**: Keep simple, automate common tasks only
- **Fallback**: Simplify, remove automation

**Risk**: Documentation too verbose
- **Impact**: Low - overwhelming for users
- **Likelihood**: Medium
- **Mitigation**: Progressive disclosure, quick start guides
- **Fallback**: Trim to essentials

</risks>
