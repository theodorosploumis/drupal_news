# Validation and Caching Systems PRD

<overview>
## Problem Statement
Drupal news aggregation requires data quality assurance and efficient fetching. Without validation, broken links and malformed data corrupt reports. Without caching, redundant HTTP requests slow execution and may hit rate limits.

## Target Users
- System operators needing reliability guarantees
- Developers debugging data quality issues
- Users wanting fast execution with cached data

## Success Metrics
- Zero invalid URLs in output
- 100% schema compliance for JSON outputs
- Cache hit rate > 60% for repeated fetches
- < 2 seconds cache lookup time
- Automatic purge of stale cache entries (> 21 days)
</overview>

<functional-decomposition>
## Capability Tree

### Capability: Data Validation
Ensure data quality and schema compliance

#### Feature: Schema Validation
- **Description**: Validate JSON objects against expected schemas
- **Inputs**: JSON object, schema definition
- **Outputs**: Boolean (valid/invalid) + error list
- **Behavior**: Check required keys, validate types, verify constraints

#### Feature: URL Validation
- **Description**: Verify URLs are reachable and valid
- **Inputs**: URL string
- **Outputs**: Boolean (valid/invalid) + HTTP status
- **Behavior**: Parse URL, check format, optionally test reachability

#### Feature: Link Presence Check
- **Description**: Ensure items have source links
- **Inputs**: Normalized item
- **Outputs**: Boolean (has valid link)
- **Behavior**: Check url field exists, is non-empty, passes URL validation

#### Feature: Markdown Validation
- **Description**: Verify Markdown structure integrity
- **Inputs**: Markdown text
- **Outputs**: Boolean + list of issues
- **Behavior**: Check for broken links, missing source citations

#### Feature: Validation Reporting
- **Description**: Generate validation reports
- **Inputs**: Validation results
- **Outputs**: validation_report.json
- **Behavior**: Aggregate counts, list failures, determine pass/fail

### Capability: Persistent Caching
Store and retrieve HTTP responses to minimize fetches

#### Feature: Cache Initialization
- **Description**: Create SQLite database for cache
- **Inputs**: Cache DB path
- **Outputs**: Initialized database
- **Behavior**: Create tables if not exist, set up indexes

#### Feature: Cache Storage
- **Description**: Store HTTP responses with metadata
- **Inputs**: URL, response data, timestamp
- **Outputs**: None (persists to DB)
- **Behavior**: Insert or update cache entry, track fetch time

#### Feature: Cache Retrieval
- **Description**: Fetch cached response if fresh
- **Inputs**: URL, TTL (time-to-live)
- **Outputs**: Cached data or None
- **Behavior**: Query by URL, check age vs TTL, return if fresh

#### Feature: Cache Invalidation
- **Description**: Remove stale cache entries
- **Inputs**: TTL threshold (days)
- **Outputs**: Count of removed entries
- **Behavior**: Delete entries older than threshold

#### Feature: Cache Statistics
- **Description**: Track cache hit/miss rates
- **Inputs**: Cache operations log
- **Outputs**: Hit rate percentage
- **Behavior**: Count hits vs misses, calculate ratio

### Capability: Metrics Collection
Track execution statistics and costs

#### Feature: Run Metrics
- **Description**: Collect per-run statistics
- **Inputs**: Run context (provider, items, duration)
- **Outputs**: metrics.json
- **Behavior**: Record timestamp, counts, token usage, costs

#### Feature: Token Tracking
- **Description**: Track AI token usage per run
- **Inputs**: Provider, model, token count
- **Outputs**: Total tokens, cost estimate
- **Behavior**: Sum input/output tokens, calculate cost

#### Feature: Cost Calculation
- **Description**: Calculate AI API costs
- **Inputs**: Provider, model, tokens
- **Outputs**: Cost in USD
- **Behavior**: Use pricing table, multiply tokens by rate

#### Feature: Performance Metrics
- **Description**: Track execution duration per module
- **Inputs**: Module name, start/end time
- **Outputs**: Duration in seconds
- **Behavior**: Calculate elapsed time, log to metrics

</functional-decomposition>

## Module Definitions

### Module: validator
- **Maps to capability**: Data Validation
- **Responsibility**: Validate data quality and schema compliance
- **Exports**:
  - `validate_items(items)` - Validate normalized items
  - `validate_urls(urls)` - Check URL validity
  - `validate_markdown(text)` - Check Markdown structure
  - `generate_report(results)` - Create validation report JSON

### Module: cache_manager
- **Maps to capability**: Persistent Caching
- **Responsibility**: Store and retrieve HTTP responses
- **Exports**:
  - `CacheManager(config)` - Initialize cache
  - `get(url, ttl)` - Retrieve cached response
  - `set(url, data)` - Store response in cache
  - `invalidate_stale(days)` - Remove old entries
  - `get_stats()` - Return hit/miss statistics

### Module: metrics_collector
- **Maps to capability**: Metrics Collection
- **Responsibility**: Track run statistics and costs
- **Exports**:
  - `record_run(run_dir, provider, items, summary)` - Save metrics.json
  - `track_tokens(provider, model, count)` - Log token usage
  - `calculate_cost(provider, model, tokens)` - Compute cost
  - `track_duration(module, seconds)` - Log execution time

### Module: utils/schema
- **Responsibility**: JSON schema definitions
- **Exports**:
  - `NORMALIZED_ITEM_SCHEMA` - Item validation schema
  - `VALIDATION_REPORT_SCHEMA` - Report schema
  - `METRICS_SCHEMA` - Metrics JSON schema

</structural-decomposition>

        /\

     /Integration\ ← 30% (Validator + cache interaction)
    /------------\

  /----------------\

## Coverage Requirements
- Line coverage: 90% minimum
- Branch coverage: 85% minimum
- Critical paths: 100% (cache retrieval, schema validation)

## Critical Test Scenarios

### Schema Validation
**Happy path**:
- Valid item with all required fields
- Expected: Pass validation

**Edge cases**:
- Missing optional fields, extra fields
- Expected: Pass if required fields present

**Error cases**:
- Missing required fields, wrong types
- Expected: Fail with specific error messages

### Cache Manager
**Happy path**:
- Store data, retrieve within TTL
- Expected: Cache hit, return stored data

**Edge cases**:
- Retrieve after TTL expired
- Expected: Cache miss, return None

**Error cases**:
- Database connection failure
- Expected: Graceful degradation, log error

### URL Validation
**Happy path**:
- Valid drupal.org URL
- Expected: Pass validation

**Edge cases**:
- URL with fragments, query params
- Expected: Pass if well-formed

**Error cases**:
- Malformed URL, wrong protocol
- Expected: Fail with parse error

## Test Generation Guidelines
- Mock SQLite for cache tests (use :memory: database)
- Test schema validation with jsonschema library
- Verify cache expiration with time mocking
- Test metrics calculation with fixed inputs

</test-strategy>

<architecture>
## System Components
- **Validator**: jsonschema for schema validation, validators for URL checks
- **Cache**: SQLite via sqlite-utils for persistence
- **Metrics**: JSON file storage for run metrics

## Data Models

```python
NormalizedItemSchema = {
    "type": "object",
    "required": ["title", "url", "date", "source_type"],
    "properties": {
        "title": {"type": "string"},
        "url": {"type": "string", "format": "uri"},
        "description": {"type": "string"},
        "date": {"type": "string", "format": "date-time"},
        "source_type": {"enum": ["rss", "page"]},
        "source_url": {"type": "string"}
    }
}

ValidationReport = {
    "rss_count": int,
    "page_count": int,
    "missing_links": int,
    "invalid_urls": int,
    "passed": bool
}

MetricsData = {
    "timestamp": str,
    "provider": str,
    "model": str,
    "duration_s": int,
    "items_total": int,
    "tokens_used": int,
    "cost_usd": float,
    "exit_code": int
}

CacheEntry = {
    "url": str,          # Primary key
    "data": str,         # Cached response
    "fetched_at": str,   # ISO timestamp
    "ttl_days": int      # Cache duration
}
```

## Technology Stack
- **jsonschema>=4.23**: JSON schema validation
- **sqlite-utils>=3.36**: SQLite database operations
- **validators**: URL validation library

**Decision: SQLite for caching**
- **Rationale**: Lightweight, no external dependencies, persistent
- **Trade-offs**: Single-threaded writes (acceptable for use case)
- **Alternatives considered**: Redis (too heavy), filesystem cache (no TTL)

**Decision: File-based metrics**
- **Rationale**: Simple, no database needed, easy to parse
- **Trade-offs**: No querying across runs (acceptable)
- **Alternatives considered**: Time-series DB (over-engineered)

</architecture>

<risks>
## Technical Risks
**Risk**: Cache database corruption
- **Impact**: High - loss of cached data
- **Likelihood**: Low
- **Mitigation**: Regular backups, corruption detection
- **Fallback**: Delete cache.db and rebuild

**Risk**: Schema evolution
- **Impact**: Medium - validation breaks with schema changes
- **Likelihood**: Medium
- **Mitigation**: Version schemas, migration scripts
- **Fallback**: Relaxed validation mode

## Dependency Risks
**Risk**: jsonschema API changes
- **Impact**: Medium - validation logic breaks
- **Likelihood**: Low
- **Mitigation**: Pin version, monitor deprecations
- **Fallback**: Custom validation fallback

## Scope Risks
**Risk**: Over-aggressive caching
- **Impact**: Medium - stale data in reports
- **Likelihood**: Medium
- **Mitigation**: Configurable TTL, force-refresh flag
- **Fallback**: Reduce default TTL

**Risk**: Insufficient validation
- **Impact**: High - bad data in reports
- **Likelihood**: Low
- **Mitigation**: Comprehensive validation tests
- **Fallback**: Manual validation step

</risks>
